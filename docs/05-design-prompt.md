---

Build a **single-file HTML clickable prototype** (inline CSS + JS, no external assets except Google Fonts, no localStorage — in-memory state only) of a developer tool called **Quorum**. This is a design validation mockup, not a real app: everything is populated with the realistic fake data specified below, and navigation between screens must work by clicking.

## What the product is

Quorum is an open-source, local-first "mission control" for agentic software engineering. A developer opens a project folder and: (1) maintains one canonical **harness** — rules, context, command prompts, flow definitions — which the tool compiles into each AI vendor's dialect (CLAUDE.md, AGENTS.md, GEMINI.md stay in their standard places as thin generated files linking back to the canonical sources); (2) keeps a **backlog** of tickets as folders in git, each ticket moving through stages (draft → requirements → solutioned → red → green → reviewed → qa-passed → deployed); (3) defines **flows**: declarative, git-versioned orchestrations of coding agents, one per stage, e.g. "two PMs + a head-of-product judge" or "two competing coders + a judge + a review panel"; (4) **runs** flows using multiple vendors' CLI agents (Claude Code, Codex CLI) on subscription OAuth — never API keys; every code-writing step runs in its own git worktree, and the run's product is a branch/PR, never a mutated working tree; (5) watches everything live and **gates every step**: the run pauses so the human sees verdicts, diffs and reasoning, then answers it with one of exactly three words — `advance`, `retry` or `abort`, and there is no fourth. The name is the rule: nothing advances without a quorum — enough agreement between vendors, and the human's say.

Tone of the product: calm, precise, trustworthy. The user is a professional developer supervising a team of AI agents — not chatting with a bot.

## Aesthetic direction

Dark theme, "ground control" feel. Near-black desaturated background (not pure black), one restrained accent color (electric teal or amber — pick one, use it only for live/active states and primary actions). Inter or IBM Plex Sans for UI, JetBrains Mono for code/traces/costs. Density like Linear or Vercel's dashboard: information-rich but generous line-height, no clutter, no gradients-for-decoration, no glassmorphism. Status colors: running = accent pulse, waiting-on-human = amber, passed = green, failed = red, idle = gray. Every vendor gets a small badge (Claude = coral square, Codex = white circle, Gemini = blue diamond) shown wherever an agent appears.

## Layout skeleton (all screens)

Left rail (56px, icons): Projects, Backlog, Harness, Flows, Runs, History, Settings. Top bar: current project name ("acme-billing"), git branch, a subscriptions status cluster (Claude ✓ logged in, Codex ✓ logged in, Gemini — not installed), and a global "Run flow ▸" primary button. Main area varies per screen.

## Screens (each a route; left rail navigates)

**1. Projects home.** Grid of project cards (acme-billing, heyruud.com, northwind-crm) each showing: path, harness health ("harness in sync" or "2 vendor files drifted — recompile"), backlog summary (3 tickets waiting on a gate), last run summary, cost this week split by vendor (Claude in dollars, Codex in tokens — never summed). One "Open a folder…" card.

**2. Backlog board.** Kanban with one column per stage (draft · requirements · solutioned · red · green · reviewed · qa-passed · deployed). Each ticket card: id (`Q-0042`), title, owner, iteration counters (review 1/3), cost to date per vendor, and a "Run next flow ▸" button enabled only when a flow consumes that stage. Clicking a card opens the **ticket page**: the ticket folder rendered as tabs (Requirements — candidate-claude / candidate-codex / merged side by side; Solution — solution.md, contracts list, tasks table with role badges and dependency arrows; QA — scenarios × red/green/final matrix; Dev — integration notes; Review — rounds as columns) plus a runs.log timeline down the right edge.

*What shipped diverges from that paragraph in four measured ways, recorded here so a screen ticket does not rediscover them (Q-0017). **Ten columns, not eight**: `packages/shared/src/stages.ts` declares `blocked` and `abandoned` beside the eight above, and this repository's own backlog holds four `abandoned` tickets, so a board built from the list above loses them silently. **Counters carry no denominator**: `review 1/3`'s `3` is a step's `max_iterations` inside a flow file, `GET /flows` carries no steps, and `docs/04-architecture.md` forbids a placeholder showing a value nobody measured — so the card renders `review 1`. **The cost figure is neither per vendor nor cost to date**: a ticket's `history` records one billed number, 276 of 665 billed occurrences in this repository are unpriced and invisible to it, and the roll-up that could split by vendor is per run rather than per ticket — so the card renders the one figure the board already prints, with the legend naming what it omits, and the per-vendor ticker stays screen 5's, where a run is the unit. **No "Run next flow ▸" button**: two flows consume `requirements` — `chore` and `solutioning` — so one button would take the most consequential routing choice in this product silently; the column names every flow that consumes it instead, and starting a run needs somewhere to watch it. **Q-0130 built the control and it is on the ticket page, not on a card**, which is measured rather than a preference: that column naming is rendered per COLUMN and so attaches to no ticket at all, so it cannot be made actionable where it is; and a card is a single `<a>` by design, so a reader can middle-click it, which leaves a control on one either nested inside a link or beside it changing what a card is. The ticket page already carries the stage, is one click away, and is where a reader has just read the ticket — and there the choice of flow is a reader's, every consuming flow being offered rather than one. The board is unchanged and still writes nothing.*

Below: horizontal step timeline showing developers (running) → integrate (queued) → gate. One event in the Claude column is expanded showing a diff snippet.

*What shipped diverges from that paragraph's **stop button** in three measured ways, recorded here so a screen ticket does not rediscover them (Q-0130). **It is offered from the daemon's own last answer and never from the connection**: the control renders while `GET /runs/:handle` last reported the run `running` and is absent for a refused start and for one that is over, and no member of the browser's connection state decides it — `docs/GLOSSARY.md` says that union *"is not run state"* in as many words, so a screen that hid the control when its socket dropped would withhold the one act a reader wants precisely when they can no longer watch. **It is confirmed rather than immediate**, naming the handle, with at most one act in flight and every lifecycle control on the screen inert while one is out; the guard is released by that request's own resolution and by nothing else, which is Q-0016's review blocker on this screen's neighbour. **And what it establishes is delivery, not an ending**: the route answers `204` once the daemon has aborted the run's own `AbortSignal`, and work already under way unwinds before a run closes — so the screen says the cancellation was taken and that where the run is now is a read, and a `not-running` refusal is rendered as what it is rather than as proof the run completed. It is never worded with `advance`, `retry` or `abort`: a stop is not a gate answer, and `gateAnswerEnvelopeSchema` is closed over those three.*

**6. Gate screen (second hero).** Reached when a judge or integrate step finishes: verdict card "Review panel: changes requested — 2 blockers, 5 majors deduplicated from 11 findings" with the blockers listed; side-by-side diff summary (files changed, +/- lines, one expanded hunk); the judge's full reasoning in a collapsible; three actions, and they are the three answers a gate takes rather than three the screen invents: primary "Send back to development (round 2/3)" (`retry`), secondary "Advance" (`advance`), tertiary "Abort the run" (`abort`). There is no fourth action and no reason field — a gate answer is one word and carries nothing else. A small "why human gates" hint: gates can be set to auto per-step in the flow file; deploy's gate is human-locked.

*What shipped diverges from that paragraph in three measured ways, recorded here so a screen ticket does not rediscover them (Q-0016). **`retry` is not the primary action, and at most gates it is not offered at all**: `packages/core/src/engine/routing.ts` reads the step's own `retryTarget` and answers a `retry` at a gate that names none with `return { abort: true }` — it ends the run — so the control is rendered only where the question carries a target. Re-derived rather than transcribed, over this repository's own run logs: `grep -hE 'gate=[a-z-]+ answer=(advance|retry|abort)' backlog/*/runs.log | wc -l` counts **220** engine-recorded answers, of which **148** are at author-declared gates where `retry` was chosen **zero** times, and no flow file in `harness/flows/` sets `retryTarget` on any gate step. The bare `grep -c 'gate='` returns 255 and is not the figure: it also collects 34 retry-grant lines and one hand-written erratum note. **Reached when a run parks, not when a judge or integrate step finishes**: that names the minority case, and a gate a flow declares follows any step at all. **No diff summary and no collapsible reasoning** — neither is on this transport, and rendering one needs a range the wire does not carry and this workspace's first diff dependency; that half is **Q-0134**'s, and until it lands the screen shows no region standing in for what it does not have. What the screen adds beyond the mockup is the four things a run can be doing other than waiting — under way with nothing asked, over, refused, or a handle nothing minted — each with a sentence rather than an empty page.*

*Q-0129 closed the first half of that third divergence, and what it shipped diverges from the mockup in its own way. **The decision the step returned is rendered, and nothing is deduplicated or counted**: the gate question carries `reached` — the deciding step's id, its verdict word, its summary and every entry it reported — so the screen reads a value rather than parsing a sentence (see *"A gate question carries the decision that reached it"*, 2026-09-17). What it does not do is the headline this paragraph sketches. **No `2 blockers, 5 majors deduplicated from 11 findings`**: measured over this repository's own **1,080** reported entries, `nit` 366, `observation` 303, `major` 210, `blocker` 51 and **150 carrying no prefix the product declares** — one in seven — so a count over that vocabulary is a number that is wrong without saying so, and an entry matching none is rendered whole under a heading of its own rather than dropped or re-filed. **Nothing is collapsed and nothing is capped**: the largest such record in this repository's history is 13 KB against ticket folders reaching 3.1 MB, so there is no size to manage, which is Q-0127's precedent — satisfy the disclosure rule by having no cap rather than by disclosing one.*
