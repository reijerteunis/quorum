# Review findings

- **major** — `packages/core/src/engine/routing.ts:7`: Gate sequence numbers are stored by `RoutingContext` identity, but `engine.ts:163` creates a fresh spread context for every step and every traversal. Consequently, separate gates in one run commonly receive the same `<runId>:1` ID, so stale answers can be accepted for a later gate and the promised run-wide correlation is not unique. Store the sequence in shared run state or allocate gate IDs from the original run context.

- **major** — `packages/core/src/engine/engine.ts:158`: The orchestration loop never checks the combined abort signal. Cancellation is currently observed only while `askGate` is pending; an already-aborted empty run completes successfully, and cancellation between steps can allow the next step to start. Check cancellation before initialization/step execution and route it through the interrupted terminal lifecycle.

- **major** — `packages/core/src/engine/engine.ts:98`: The local `active` occurrence set is never populated, and neither the context nor persistence interface exposes allocation/registration of an occurrence. Therefore `finaliseActiveOccurrences` at lines 113–117 is permanently a no-op, leaving later Q-0052/Q-0053 steps no way to satisfy the requirement that active occurrences become failed or interrupted before terminal persistence. Expose and compose the landed run-history occurrence lifecycle so executed steps register in the same set that finalisation closes.

- **major** — `packages/core/src/engine/engine.ts:195`: After emitting and persisting a failed terminal outcome, the engine rethrows the original value. Non-`FlowError` failures such as loader `ENOENT` therefore surface as raw errors, contrary to AC-3 and the solution’s terminal-then-`FlowError` contract. Translate ordinary failures to a cause-bearing `FlowError` before completing the channel, while retaining only explicitly authorised preserved exception shapes.

- **major** — `packages/core/src/engine/lifecycle.ts:78`: `recordEvent` mutates history and performs ticket/log writes itself, then calls `persistence.recordOccurrenceEvent`; the concrete implementation of that capability in `engine.ts:107-112` repeats the same history mutation and writes. Calling the exported helper with the real context thus appends two history entries and two log lines. Define one layer as the sole owner of the mutation and make the other delegate without repeating it.

- **major** — `packages/core/src/engine/channel.ts:94`: The claimed single-consumer contract is not enforced. Every `Symbol.asyncIterator` call returns access to the same `next` function, and concurrent pending pulls overwrite the single `pending` slot at line 80, leaving the earlier promise unresolved indefinitely. Return one stable iterator or explicitly reject a second iterator/pending pull.

- **major** — `docs/03-adapter-contract.md:38`: The required third documentation surface was not updated. It still describes only a “streaming trace” and step-ID enrichment, without documenting the run event stream’s terminal member, correlated answer channel, cancellation ownership, ordering limits, or timestamp refusal. Update this document alongside the glossary and architecture document as required by AC-13.
