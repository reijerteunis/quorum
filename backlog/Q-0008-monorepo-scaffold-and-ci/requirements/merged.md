# Q-0008 — Monorepo scaffold and CI

*Merged requirement (head-of-product). Stage draft → requirements. Milestone M2. Route: requirements → chore → human gate, per the chore-flow decision of 2026-08-24.*

*The ticket body settles the scope, the id and the route; nothing here reopens any of the three. Both candidates respected that, and so does this. Every factual claim below was checked against `main` on 2026-08-24 — see §Confirmation.*

## Problem

**The repository has no build.** The root holds `.claude/`, `backlog/`, `contracts/`, `docs/`, `harness/`, `spike/`, `.gitignore`, `CLAUDE.md` and `README.md` — no `package.json`, no `tsconfig*.json`, no ESLint configuration, no `turbo.json`, no `.nvmrc`, no `.github/`. Everything Quorum can run is `spike/`: plain Node ESM on npm with its own `package-lock.json`, three dependencies (`ajv`, `ajv-formats`, `yaml`), `engines.node: ">=20"`, and a hand-rolled runner that discovers `test/*.js`. CLAUDE.md's instruction not to extend the spike beyond M0/M1 needs became binding when M1 closed on 2026-08-24, so the next line of engine code has nowhere to live.

Three consequences, all true on `main` today:

- **Q-0009 has nothing to port into.** "Port core to TypeScript with schemas" presumes a package with a TypeScript compiler, a test runner and a lint pass. None of the three exists.
- **Q-0010 has no package boundary to publish.** A `quorum` binary cannot come from a repository whose only `package.json` is named `"quorum (spike)"` and whose only binary is `harness`.
- **Nothing verifies a push.** There is no CI. Every test this repository has run, ran on one laptop because someone remembered to run it. The spike suite is the only regression evidence M1 produced, and its greenness is a habit rather than a fact.

There is a fourth problem specific to this ticket, and it is the one most likely to cost money: **this is the easiest ticket in M2 to overbuild.** The chore flow deliberately drops the two mechanisms that normally hold scope — no contract to code against, no failing test to satisfy — so the only things between a scaffold and a half-started port are the criteria below and the reviewer who reads them. Every criterion here is therefore a command, not a description.

**Surfaces touched:** repository tooling only. Root workspace files, `packages/**`, `apps/web/**`, `.github/**`, two keys in `harness/harness.yaml`, and a status-line touch on `docs/04-architecture.md`. Explicitly untouched: CLI behaviour (Q-0010), engine code (Q-0009), any flow, role or context file in `harness/`, any `backlog/` file format, any UI (M3), and `README.md`.

## User stories

**Maintainer.** As a solo maintainer, I clone the repository on Node 22 and `pnpm install && pnpm lint && pnpm typecheck && pnpm test` all work — CLAUDE.md's Commands section stops being aspirational. When I push a branch, GitHub runs those three plus the spike suite and tells me if I broke either. Nothing I already rely on changes: `node spike/bin/harness.js run …` behaves exactly as it did yesterday.

**Contributor.** As an adapter contributor arriving from the README, the repository tells me where code goes — seven named packages matching `docs/04-architecture.md` — and what the rules are *enforced by*, not just where they are written down: one ESLint configuration that fails the build on `any` and on an undescribed `@ts-ignore`, which is what `harness/rules.md` has always asked for and nothing has ever checked.

**Adopter.** As a stranger trying Quorum on my own repository, nothing changes and nothing gets longer. The README still points at the spike, the first thirty minutes are the same thirty minutes, and this ticket adds no step to them. The scaffold is a contributor's concern, not an adopter's.

## Acceptance criteria

Ten criteria — the ceiling the ticket sets — each verifiable by one command from a clean clone on Node 22.

### Workspace

**1. The workspace installs from a frozen lockfile, and it installs exactly eight things.**
Root `package.json` is `private: true`, `type: "module"`, `engines: { "node": ">=22" }`, carries `packageManager: "pnpm@<pinned exact version>"`, and defines `lint`, `typecheck` and `test` scripts that each delegate to `turbo run <task>`. It declares **no** `bin` field — the binary is Q-0010's. `.nvmrc` contains `22`. `pnpm-workspace.yaml` lists exactly `packages/*` and `apps/*`; `spike` is neither a member nor matched by a glob. `pnpm-lock.yaml` is committed and was generated by the pinned pnpm.
*Verify:* `rm -rf node_modules && pnpm install --frozen-lockfile && pnpm ls -r --depth -1` exits 0 and lists the root plus seven workspace packages, none of them `spike`.

**2. Seven packages exist, exactly seven, and each is empty on purpose.**
`packages/core`, `packages/server`, `packages/cli`, `packages/compiler`, `packages/templates`, `packages/shared`, `apps/web`. Each has a `package.json` (`private: true`, name `@quorum/<dir>`, `type: "module"`, `lint`/`typecheck`/`test` scripts); a `tsconfig.json` whose only meaningful key is `"extends": "../../tsconfig.base.json"`; a `src/index.ts` placeholder exporting a name constant and nothing else; and one Vitest test that asserts that placeholder and passes. No package declares runtime `dependencies` — a scaffold has none, and the first one to appear is a port that started early. Names are unique and share one namespace. No eighth directory under `packages/` or `apps/` is registered. `apps/web` additionally has a minimal `vite.config.ts` and nothing more — no React shell, no router, no theme (M3, Q-0014). `packages/templates` ships no harness assets: `spike/templates/harness/**` stays where it is until Q-0009 moves it.
*Verify:* `pnpm test` reports seven passing suites; `pnpm ls -r --depth -1 | wc -l` prints `8`; `grep -rn "spike" packages apps --include=*.ts --include=*.json` prints nothing; `grep -l '"dependencies"' packages/*/package.json apps/web/package.json` prints nothing; `wc -l packages/*/src/index.ts apps/web/src/index.ts` totals under 50 lines.

### TypeScript and lint

**3. Strict TypeScript comes from exactly one file, and it bites.**
`tsconfig.base.json` at the root sets `strict: true`; `typecheck` is `tsc --noEmit`. `module` and `moduleResolution` are chosen explicitly and stated with a one-line reason in `dev/implement-report.md` — an unstated default here is a default nobody chose, and it propagates into every package Q-0009 ports. Any additional strictness flag is the implementer's call, stated with a reason in the same report. No package tsconfig re-declares or weakens a compiler option.
*Verify:* `pnpm typecheck` exits 0; `grep -n 'compilerOptions' packages/*/tsconfig.json apps/web/tsconfig.json` prints nothing; and, temporarily, appending `const n: number = "x";` to `packages/core/src/index.ts` makes `pnpm typecheck` exit non-zero — reverted, and the check recorded in the implementer's report.

**4. One ESLint configuration, and it enforces the two rules this repository already wrote down.**
`eslint.config.js` at the root is the only ESLint configuration file in the repository — flat config, applying to `packages/**` and `apps/**`, ignoring `spike/**`, `**/dist` and `node_modules`. It sets `@typescript-eslint/no-explicit-any` to error and configures `@typescript-eslint/ban-ts-comment` so a `@ts-ignore` or `@ts-expect-error` requires a description. Those are exactly the two rules `harness/rules.md` states and nothing currently enforces. Type-aware linting is deliberately **off**: `tsc` owns types, ESLint owns style, and a type-aware pass doubles CI time for a repository whose packages are empty. Q-0009 may turn it on if it earns it.
*Verify:* `git ls-files | grep -i eslint` prints one path; `pnpm lint` exits 0; temporarily adding `const x: any = 1;` to `packages/shared/src/index.ts` makes `pnpm lint` exit non-zero.

### Test runner and task graph

**5. Vitest is configured once, runs through turbo, and runs once.**
One shared Vitest configuration; a package-level config is at most a two-line re-export of it. Every package's `test` script invokes `vitest run` — **not** bare `vitest`, which watches and would hang CI and the `integrate` step's 15-minute command timeout. `pnpm test` runs every package's suite and no workspace is silently skipped; a single package is runnable on its own.
*Verify:* `pnpm test` exits 0 within a few seconds, reports seven test files, and returns to the prompt without watching; `pnpm --filter @quorum/core test` runs exactly one.

**6. Turbo's cache is on, and its hits are honest.**
`turbo.json` declares `lint`, `typecheck` and `test`, each with explicit `outputs` (an empty array where a task emits nothing), so a cache hit means the task genuinely had nothing to do. `inputs` stay at the default — a clever narrowing here is how a cache reports success for a task that never saw the changed file. `.gitignore` gains `.turbo/`, `coverage/` and `*.tsbuildinfo` beside the existing `node_modules/`, `.quorum/`, `.harness/`, `dist/`, `*.log`, `.env*`. **No `build` task ships**: nothing emits yet, and Q-0009 adds it with the first package that does. No remote cache, no account, no signing secret.
*Verify:* `pnpm test && pnpm test` — the second run reports every task cached (`FULL TURBO`); `git check-ignore .turbo coverage` exits 0; `grep -c '"build"' turbo.json` prints `0`.

### CI

**7. One workflow runs the three tasks on push and pull request, with no secret in sight.**
`.github/workflows/ci.yml` triggers on `push` and `pull_request`. One Node version, taken from `.nvmrc` via `actions/setup-node`'s `node-version-file` so the pin lives in one place; pnpm from the root `packageManager` field; `pnpm install --frozen-lockfile`; then `pnpm lint`, `pnpm typecheck`, `pnpm test`, with `.turbo` restored between runs by `actions/cache`. The workflow references no `secrets.*` and defines no environment variable whose name contains `KEY` or `TOKEN` — BYOS has no CI exception, and a scaffold is exactly where such a variable would first appear unremarked. No release, publish, deploy or dependency-update automation.
*Verify:* `grep -c 'secrets\.' .github/workflows/ci.yml` prints `0`; `grep -iE '(KEY|TOKEN)' .github/workflows/ci.yml` prints nothing; once the ticket branch is pushed, `gh run list --branch harness/Q-0008/integration --limit 3` shows both jobs green. If the branch is unpushed when the gate is reached, the reviewer runs each `run:` line locally instead and the gate records that it did.

**8. The spike is untouched and still green, and the repository's test command now covers both suites.**
No file under `spike/` changes. `spike/` stays outside the pnpm workspace, outside ESLint's scope and outside turbo's task graph, and keeps npm and its own `package-lock.json`. Two things follow.

*In CI:* the same workflow runs the spike as a **second job** — `npm ci` then `npm test` inside `spike/`, on the same Node version — because until Q-0009 ports it, the spike suite is the only regression evidence this repository has, and a green badge proving seven placeholder tests pass while the real suite goes unrun is worse than no badge. That job first sets a git identity (`git config --global user.email … && git config --global user.name …`), since the suite drives the engine through real commits in real worktrees and a fresh runner has no identity configured. Running it on Node 22 also surfaces any incompatibility the spike's `engines: ">=20"` currently permits — surfaced, not fixed, and not by editing a spike file.

*In the harness:* `harness/harness.yaml`'s `commands.install` and `commands.test` are extended to cover the workspace as well as the spike — install both dependency sets (`pnpm install --frozen-lockfile` beside the existing `npm install --prefix spike …`), and run both suites so the step fails if either fails. `&&` chaining is sufficient: `runCommand` goes through `execSync`, which uses a shell (`spike/src/fanout.js:126`). Today both keys name the spike alone, so an `integrate` step with `expect: pass` proves the spike is green and says nothing whatever about the scaffold — which is precisely the claim the chore-flow decision says that step exists to make. **This takes effect from the next run onward, not this one:** `bin/harness.js:56` reads `harness/harness.yaml` once at run start, so Q-0008's own `integrate` still runs the old spike-only command. The scaffold's greenness in *this* ticket is proved by criterion 7's CI and by the reviewer at the gate; the edit is what makes it proved automatically for Q-0009 and everything after.
*Verify:* `git diff --name-only main...HEAD -- spike/` prints nothing; `npm test --prefix spike` exits 0; the two command strings now in `harness/harness.yaml` both exit 0 when run from a clean clone; the workflow's spike job is green on the ticket branch.

## Risks

- **Scope creep dominates, and the chore flow has no red phase to catch it.** Nothing here fails before the change and passes after, so criterion 10 is the entire safety net. *Mitigation:* the reviewer's first action is the changed-path check, before opening a single file.
- **pnpm does not hoist.** A package whose `test` script runs `vitest` needs `vitest` resolvable *from that package*; root-only devDependencies install cleanly and then fail at `pnpm test`, which is a confusing failure to meet on a first clone. *Mitigation:* the implementer picks per-package devDependencies or a pnpm catalog, states which in one line, and criterion 1's verification runs from a genuinely empty `node_modules`.
- **Lockfile drift breaks CI on the first push.** `--frozen-lockfile` fails if `pnpm-lock.yaml` was not regenerated after the last `package.json` edit, or was written by a different pnpm major than `packageManager` pins. *Mitigation:* regenerate and commit the lockfile as the last step before integrate.
- **Node skew.** The maintainer's machine runs v24.15.0 today. `engines` must be `">=22"`, never `"22.x"`, or the scaffold refuses to install on the machine that built it. Separately, the spike declares `">=20"` and has never been exercised on 22 in CI; criterion 8 is where that surfaces, and surfacing it is the correct outcome — fixing it is not this ticket's business.
- **Git identity in CI.** The spike suite passes `-c user.email`/`-c user.name` on its own git invocations, but the engine it drives commits worktrees with the ambient identity, and a bare runner has none. Criterion 8 handles it, and it is the most likely reason for a first red CI run.
- **A turbo cache hit can hide a real failure** if `inputs` are narrowed. Criterion 6 keeps them at the default for exactly this reason.
- **Vitest in watch mode hangs CI and `integrate` alike.** `commands.timeout_ms` is 900000, so a watching suite burns fifteen minutes before it is killed and reports as a timeout rather than a mistake. Criterion 5 requires `vitest run`.
- **CI honesty.** Until Q-0009 lands, the seven package suites assert placeholders. Drop criterion 8's spike job and the badge means "the scaffold parses" while claiming to mean "the tests pass".
- **Configuration drift over time.** This ticket prevents *initial* TypeScript and ESLint divergence; it adds no governance system that keeps a future package from adding its own config. Criterion 4's single-file check is the only guard, and it is a point-in-time one.
