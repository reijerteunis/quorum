# Q-0008 — Monorepo scaffold and CI

*Candidate requirement (product-manager, Claude). Ticket Q-0008, stage draft → requirements. Milestone M2. Route: requirements → chore → human gate, per the chore-flow decision of 2026-08-24.*

*Scope note: the ticket body settles the scope, the id and the route, and this requirement does not re-open any of the three. What follows turns that scope into criteria a reviewer can run. Every claim about the repository was checked against `main` — see §Confirmation.*

## Problem

**The repository has no build.** The root holds `.claude/`, `backlog/`, `contracts/`, `docs/`, `harness/`, `spike/`, `CLAUDE.md`, `README.md` and `.gitignore` — no `package.json`, no `tsconfig.json`, no ESLint configuration, no `.github/`. Everything Quorum can actually run is `spike/`: plain Node ESM on npm with its own `package-lock.json`, three dependencies, `engines: ">=20"`, and a hand-rolled runner that discovers `test/*.js`. CLAUDE.md's instruction not to extend the spike beyond M0/M1 needs became binding when M1 closed on 2026-08-24, so the next line of engine code has nowhere to live.

Three consequences, all of them true on `main` today:

- **Q-0009 has nothing to port into.** "Port core to TypeScript with schemas" presumes a package with a TypeScript compiler, a test runner and a lint pass. None of the three exists.
- **Q-0010 has no package boundary to publish.** A `quorum` binary cannot come from a repository whose only `package.json` is named `"quorum (spike)"` and whose only binary is called `harness`.
- **Nothing verifies a push.** There is no CI. Every test this repository has ever run, ran on one laptop because someone remembered to run it. The spike suite is the only regression evidence M1 produced, and its greenness is a habit rather than a fact.

There is a fourth problem specific to this ticket, and it is the one most likely to cost money: **this is the easiest ticket in M2 to overbuild.** The chore flow deliberately drops the two mechanisms that normally hold scope — there is no contract to code against and no failing test to satisfy — so the only things standing between a scaffold and a half-started port of the engine are the criteria below and the reviewer who reads them. Every criterion here is therefore written as a command, not as a description.

## User stories

**Maintainer.** As a solo maintainer, I clone the repository on Node 22 and `pnpm install && pnpm lint && pnpm typecheck && pnpm test` all work — CLAUDE.md's Commands section stops being aspirational. When I push a branch, GitHub runs the same three commands plus the spike suite, and tells me if I broke either. Nothing I already rely on changes: `node spike/bin/harness.js run …` behaves exactly as it did yesterday.

**Contributor.** As an adapter contributor arriving from the README, the repository tells me where code goes — seven named packages matching `docs/04-architecture.md` — and what the rules are enforced by, not just where they are written down: one ESLint configuration that fails the build on `any` and on an undocumented `@ts-ignore`, which is what `harness/rules.md` has always asked for and nothing has ever checked.

**Adopter.** As a stranger trying Quorum on my own repository, nothing changes and nothing gets longer. The README still points at the spike, the first thirty minutes are the same thirty minutes, and this ticket adds no step to them. The scaffold is a contributor's concern, not an adopter's.

## Acceptance criteria

Surfaces touched: **repository tooling only** — root workspace files, `packages/**`, `apps/web/**`, `.github/**`, and a status-line touch on two documents. No CLI behaviour (Q-0010), no flow or role in `harness/`, no `backlog/` file format, no engine code (Q-0009), no UI (M3). Ten criteria, the ceiling the ticket sets, each verifiable by one command from a clean clone on Node 22.

### Workspace

1. **The workspace installs from a frozen lockfile, and it installs exactly eight things.** Root `package.json` is `private: true`, `type: "module"`, `engines: { "node": ">=22" }`, carries `packageManager: "pnpm@<pinned exact version>"`, and defines `lint`, `typecheck` and `test` scripts that each delegate to `turbo run <task>`. It declares **no** `bin` field — the binary is Q-0010's. `.nvmrc` contains `22`. `pnpm-workspace.yaml` lists exactly `packages/*` and `apps/*`; `spike` is not a member and is not matched by a glob. `pnpm-lock.yaml` is committed and was generated by the pinned pnpm.
   *Verify:* `rm -rf node_modules && pnpm install --frozen-lockfile && pnpm ls -r --depth -1` exits 0 and lists the root plus seven workspace packages, none of them `spike`.

2. **Seven packages exist, and each is empty on purpose.** `packages/core`, `packages/server`, `packages/cli`, `packages/compiler`, `packages/templates`, `packages/shared` and `apps/web`. Each has: a `package.json` (`private: true`, name `@quorum/<dir>`, `type: "module"`, `lint`/`typecheck`/`test` scripts); a `tsconfig.json` whose only meaningful key is `"extends": "../../tsconfig.base.json"`; a `src/index.ts` placeholder that exports a name constant and nothing else; and one Vitest test that asserts that placeholder and passes. `apps/web` additionally has a minimal `vite.config.ts` and nothing more — no React shell, no router, no theme (M3, Q-0014). `packages/templates` ships no harness assets: `spike/templates/harness/**` stays where it is until Q-0009 moves it.
   *Verify:* `pnpm test` reports seven passing suites; `grep -rn "spike" packages apps --include=*.ts --include=*.json` prints nothing; `wc -l packages/*/src/index.ts apps/web/src/index.ts` totals under 50 lines.

### TypeScript and lint

3. **Strict TypeScript comes from exactly one file, and it bites.** `tsconfig.base.json` at the root sets `strict: true`; any additional strictness flag is the implementer's call, stated with a one-line reason in `dev/implement-report.md`. `module`/`moduleResolution` are chosen explicitly and stated with a reason in the same report — an unstated default here is a default nobody chose, and it propagates into every package Q-0009 ports. No package tsconfig re-declares or weakens a compiler option.
   *Verify:* `pnpm typecheck` exits 0; `grep -rn '"strict"\|noImplicitAny\|"compilerOptions"' packages/*/tsconfig.json apps/web/tsconfig.json` prints nothing but the `extends`-only files' absence of those keys; and, temporarily, appending `const n: number = "x";` to `packages/core/src/index.ts` makes `pnpm typecheck` exit non-zero (reverted, and the check recorded in the implementer's report).

4. **One ESLint configuration, and it enforces the two rules this repository already wrote down.** `eslint.config.js` at the root is the only ESLint configuration file in the repository — flat config, applying to `packages/**` and `apps/**`, ignoring `spike/**`, `**/dist` and `node_modules`. It sets `@typescript-eslint/no-explicit-any` to error and configures `@typescript-eslint/ban-ts-comment` so a `@ts-ignore` or `@ts-expect-error` requires a description. Those are exactly the two rules `harness/rules.md` states and nothing currently enforces. Type-aware linting is deliberately **off**: `tsc` owns types, ESLint owns style, and a type-aware pass doubles CI time for a repository whose packages are currently empty. Q-0009 may turn it on if it earns it.
   *Verify:* `git ls-files | grep -i eslint` prints one path; `pnpm lint` exits 0; temporarily adding `const x: any = 1;` to `packages/shared/src/index.ts` makes `pnpm lint` exit non-zero.

### Test runner and task graph

5. **Vitest is configured once and runs through turbo.** One shared Vitest configuration; a package-level config is at most a two-line re-export of it. `pnpm test` runs every package's suite; a single package is runnable on its own.
   *Verify:* `pnpm test` exits 0 and reports seven test files; `pnpm --filter @quorum/core test` runs exactly one.

6. **Turbo's cache is on, and its hits are honest.** `turbo.json` declares `lint`, `typecheck` and `test`, each with explicit `outputs` (an empty array where a task emits nothing) so a cache hit means the task genuinely had nothing to do. `inputs` are left at the default — a clever narrowing here is how a cache reports success for a task that never saw the changed file. `.gitignore` gains `.turbo/`, `coverage/` and `*.tsbuildinfo` beside the existing `dist/` and `node_modules/`. **No `build` task ships**: nothing emits yet, and Q-0009 adds it with the first package that does.
   *Verify:* `pnpm test && pnpm test` — the second run reports every task cached (`FULL TURBO`); `git check-ignore .turbo` exits 0.

### CI

7. **One workflow runs the three tasks on push and pull request, with no secret in sight.** `.github/workflows/ci.yml` triggers on `push` and `pull_request`. One Node version, taken from `.nvmrc` via `actions/setup-node`'s `node-version-file` so the pin lives in one place; pnpm installed from the root `packageManager` field; `pnpm install --frozen-lockfile`; then `pnpm lint`, `pnpm typecheck` and `pnpm test`, with `.turbo` restored between runs by `actions/cache`. The workflow references no `secrets.*` and defines no environment variable whose name contains `KEY` or `TOKEN` — BYOS has no CI exception, and a scaffold is exactly where such a variable would first appear unremarked.
   *Verify:* `grep -c 'secrets\.' .github/workflows/ci.yml` prints `0`; once the ticket branch is pushed, `gh run list --branch harness/Q-0008/integration --limit 2` shows successful runs. If the branch is not pushed when the gate is reached, the reviewer runs each `run:` line of the workflow locally instead and the gate records that it did.

8. **The spike is untouched, still green, and CI is what proves it.** No file under `spike/` changes. `spike/` stays outside the pnpm workspace, outside ESLint's scope and outside turbo's task graph, and keeps npm and its own `package-lock.json`. The same workflow runs it as a **second job** — `npm ci` then `npm test` inside `spike/`, on the same Node version — because until Q-0009 ports it, the spike suite is the only regression evidence this repository has, and a green badge that proves seven placeholder tests pass while the real suite goes unrun is worse than no badge. That job first sets a git identity (`git config --global user.email … && git config --global user.name …`), since the suite drives the engine through real commits in real worktrees and a fresh runner has no identity configured.
   *Verify:* `git diff --stat main...HEAD -- spike/` prints nothing; `cd spike && npm test` exits 0; the workflow's spike job is green on the ticket branch.

### Documentation and scope

9. **The documents this makes false are fixed in the same change.** `docs/04-architecture.md`'s status line records that the scaffold now exists, with the date and what changed. CLAUDE.md's sentence "Until M2 lands, the runnable code is the spike in `spike/`" is amended to say the workspace exists and is empty, that the spike remains the regression suite until Q-0009, and that `pnpm lint` lints TypeScript while flows are still linted by `node spike/bin/harness.js lint` — two commands called "lint" in one repository is a trap worth one sentence. One `docs/DECISIONS.md` entry, in the house format (**Decision** / **Alternatives considered** / **Why**), records the single architectural choice this ticket makes: *the spike stays outside the workspace on npm, and CI runs it as its own job, until Q-0009 retires it* — against the alternatives of making it a workspace package (its runner is not Vitest, its `lint` script is the flow linter, and `--frozen-lockfile` would then govern a lockfile npm wrote) and of not running it in CI at all. New devDependencies get their one-line justification in `dev/implement-report.md`; none needs its own decision entry, because `docs/04-architecture.md` already names pnpm, Turborepo, TypeScript, Vitest, ESLint and Vite. The README is not touched.
   *Verify:* `head -5 docs/04-architecture.md` shows the bumped status line; the new `docs/DECISIONS.md` heading carries all three required sections; `git diff main...HEAD -- README.md` prints nothing.

10. **Nothing else ships.** The changed-path set is exactly: root `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `tsconfig.base.json`, `eslint.config.js`, `turbo.json`, `.nvmrc`, `.gitignore`, `packages/**`, `apps/web/**`, `.github/workflows/ci.yml`, `docs/04-architecture.md`, `docs/DECISIONS.md`, `CLAUDE.md`, and this ticket's folder. No publish or release workflow, no changesets, no Dockerfile, no renovate or dependabot configuration, no commit hooks, no README rewrite, no `spike/` change, no engine code. No package declares runtime `dependencies` — a scaffold has none, and the first one to appear is a port that started early.
    *Verify:* `git diff --name-only main...HEAD` matches the list above with nothing extra; `grep -l '"dependencies"' packages/*/package.json apps/web/package.json` prints nothing.

## Non-goals

Restating the ticket's, plus the ones a scaffold attracts:

- **No publish or release pipeline**, no changesets, no versioning, no `CHANGELOG.md`, no npm name reservation. Q-0010 and M6 own that.
- **No engine code and no ported module.** Not one function from `spike/src/**` moves. Not one zod schema is written (Q-0009).
- **No `build` task and no emitted output.** `typecheck` is `tsc --noEmit`.
- **No `apps/web` beyond a Vite placeholder** — no React shell, no Tailwind, no theme, no routing.
- **No harness assets in `packages/templates`.** `spike/templates/harness/**` stays put.
- **No commit hooks** (husky, lint-staged) — CI is the enforcement point; a hook that runs on every commit lengthens every contributor's loop for a repository that currently has no code to guard.
- **No Node or OS matrix**, no coverage thresholds, no type-aware lint, no remote turbo cache.
- **No Docker, no renovate, no dependabot, no README rewrite.**

## Open questions

None of these blocks implementation; each has a recommendation the implementer follows unless the owner says otherwise at the gate.

1. **Package scope: `@quorum/*` or `@heyruud/*`?** — *Owner: Ruud. Not a blocker.* Recommendation: `@quorum/*`, all private. Nothing publishes here, so the scope names nothing on npm; the 2026-08-22 naming decision leaves the *published* name (`quorum`, falling back to `@heyruud/quorum`) to Q-0010, and renaming private workspace packages is a one-line change per package.
2. **Turbo remote caching?** — *Owner: Ruud. Not a blocker.* Recommendation: no. It requires an account and a signing secret in CI, and criterion 7 forbids a secret on principle; a local cache plus `actions/cache` gets most of the benefit for a repository this size.
3. **Does `packages/templates` stay a TypeScript package?** — *Owner: architect, at Q-0009.* It gets `src/index.ts` here because the ticket says every package does, but its eventual content is YAML and markdown. Worth deciding when the assets actually move; nothing here depends on the answer.
4. **`docs/06-development-plan.md` describes Q-0009's port as "the 30-check smoke test".** `spike/test/` now holds three test files — `smoke.js`, `q0006-engine.js`, `q0033-surface.js` — grown by Q-0006, Q-0011 and Q-0033. The figure is stale and the port is bigger than the plan implies. *Owner: Ruud.* Not this ticket's edit: it belongs to Q-0009's requirement, and correcting it here would be scope this ticket has no business taking.

## Risks

- **Scope creep is the dominant risk**, and the chore flow has no red phase to catch it — nothing here fails before the change and passes after, so criterion 10 is the safety net. *Mitigation:* the reviewer's first action is the changed-path check, before reading any file.
- **pnpm does not hoist.** A package whose `test` script runs `vitest` needs `vitest` resolvable from that package: root-only devDependencies install cleanly and then fail at `pnpm test`, which is a confusing failure to hit on a first clone. *Mitigation:* the implementer picks per-package devDependencies or a pnpm catalog, states which in one line, and criterion 1's clean-install verification is run from a genuinely empty `node_modules`.
- **Lockfile drift breaks CI on the first push.** `--frozen-lockfile` fails if `pnpm-lock.yaml` was not regenerated after the last `package.json` edit, or was written by a different pnpm major than `packageManager` pins. *Mitigation:* regenerate and commit the lockfile as the last step before integrate.
- **Node skew.** The maintainer's machine is on v24.15.0 today. `engines` must be `">=22"`, never `"22.x"`, or the scaffold refuses to install on the machine that built it.
- **Git identity in CI.** The spike suite sets an identity per command in its own `execSync` calls, but the engine it drives commits worktrees with whatever identity is configured; a bare runner has none. Criterion 8 handles it, and it is the most likely reason for a first red CI run.
- **A turbo cache hit can hide a real failure** if `inputs` are narrowed. Criterion 6 keeps them at the default for exactly this reason.
- **CI honesty.** Until Q-0009 lands, the seven package suites assert placeholders. If the spike job in criterion 8 is dropped, the badge means "the scaffold parses" while claiming to mean "the tests pass".
